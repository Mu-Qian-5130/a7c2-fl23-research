# 自定义 LUT／DCP：从获取文件到写入相机的全流程

[返回首页](../../README.zh-CN.md) · [English](../en/custom-lut.md)

这份文档覆盖获取 DCP／LUT、色彩转换、机身备份、写入、读回、重新加载、实拍验收和还原。面向用户和代为实现的 AI；第 1–6 步已有离线工具，第 7–13 步说明需要 AI 实现与验证的设备流程。**当前公开命令行入口仍不是一键安装器；本文不把待开发步骤伪装成现成命令。**

如果你只是想在 Lightroom／Camera Raw 使用这些 DCP，直接看 [DCP 下载与安装](profiles.md)及[电脑端操作](manual.md)，无需完成这六步。如果你想安装现成的 FL2／FL3，请看[另一份安装说明](fl23.md)。

## 先分清这些东西

| 名称 | 可以怎样理解 | 从哪里来 |
|---|---|---|
| DCP／CUBE | 你想模仿的色彩参考 | 自己制作或取得合法使用的文件；[参考包](profiles.md)含 18 款原始 DCP |
| ST | Sony 创意外观里的“标准” | 相机原有外观；本方案以它为输入基础 |
| 自定 1–6／栏位 | 希望哪一个自定位置使用哪款风格 | 在项目文件中指定；查看计划不会改相机 |
| JSON | 有字段名的文字配置文件 | 用文本编辑器编辑，文件名要以 `.json` 结束，不能是 `.json.txt` |
| 校准 | 说明 Sony ST 的颜色及色表改动如何对应到目标颜色 | 需要真实量测；不是把任意 DCP 改个文件名 |
| 拟合 | 用相机有限的色表格点尽量逼近目标风格 | 工具计算，会产生误差 |
| 候选 | 计算出来、等待检查的色表和报告 | 第 5 步生成，尚未装入相机 |
| 正向／还原清单 | 记录特定原文件的哪些字节要改、如何改回 | 第 6 步生成，需要另外的设备集成才能执行 |

DCP 本来服务于 RAW 显影，并不直接等同于“Sony ST 照片 → 富士风格”。Sony 和参考显影的色彩起点不同，所以要先建立对应关系，再拟合。工具只提取 look／tone 阶段，保留 Sony 机身本来的校准，不复制其他相机的传感器校准。

## 打开终端，确认当前工具能做什么

完整解压工具后，在含 `lut.py` 的目录打开终端。按[Windows／Mac 手动操作](manual.md)给当前 Python 安装依赖，然后运行：

```text
python lut.py doctor
python lut.py --help
```

`doctor` 只检查电脑环境，`lut.py` 的现有命令都不连接相机。LUT 入口没有 GUI 或 CMD 启动层，六步转换直接对应下面六个子命令。

- 只有 DCP／CUBE：先检查文件、编辑项目并查看计划。
- 有已核对的栏位记录：可以核对绑定 JSON，但这仍不是读取相机。
- 有真实校准或量测数据：才具备拟合条件。
- 有精确支持的 AP／CP：才能准备更新清单；后面的机身实施仍需 AI 完成。

## 先准备一个只导入 Classic Neg. 的项目

先在电脑建一个自己的工作文件夹，例如 `D:/MyLook`。以下名称和组织方式只是示例：

```text
MyLook/
  project.json              自己编辑的导入计划
  bindings.json             按已核对的机身状态填写
  references/
    Sony_ILCE-7CM2_Classic_Negative_MTriton.dcp
  measurements/
    patches.npz             由量测与样本处理得到
    response.json           由 ISP 响应量测得到
  calibration-v1.json       第 4 步生成，或已有有效校准
  candidate-v1/             第 5 步生成
  transition-v1/            第 6 步生成
```

后面三项输出不必提前创建，工具要求使用新文件／新目录。把参考包中的对应 DCP 放进 `references`，然后用文本编辑器创建 `project.json`：

```json
{
  "schema": "a7c2-look-project/1",
  "model": "ILCE-7CM2",
  "firmware": "2.01",
  "calibration": "calibration-v1.json",
  "slots": [
    {
      "slot": 1,
      "name": "Classic Neg.",
      "base": "ST",
      "source": {
        "type": "dcp",
        "path": "references/Sony_ILCE-7CM2_Classic_Negative_MTriton.dcp",
        "exposure_stops": 0,
        "attribution": "MTriton / abpy; CC BY-NC-SA 4.0"
      }
    }
  ]
}
```

这里表示“只准备把自定 1 用作 Classic Neg.，基础为 ST”。`slot` 是目标栏位，`name` 是计划中的名称，`source.path` 指向参考文件，`calibration` 指向校准文件。写入名称字段不会直接更改相机菜单。

这些相对路径以 **`project.json` 所在文件夹**为起点，不以工具安装目录为起点。增加其他风格时，在 `slots` 中增加条目，每个 `slot` 必须唯一且在 1–6 内，并使用 `base: "ST"`。不要为了照抄六款示例就把所有栏位都选上。[六款模板](../../src/looks/examples/six-looks.json)只展示配置形式，里面的参考路径需要自行修改。

## 六个转换命令分别做什么

| 转换步骤 | 对应命令 | 事先准备的输入 | 输出 |
|---|---|---|---|
| 1. 检查 DCP / CUBE | `inspect` | 参考文件 | 日志中的规格、哈希 |
| 2. 查看 ST 栏位计划 | `plan` | 项目 JSON | 选中栏位和需保留栏位 |
| 3. 核对 ST 绑定文件 | `check-bindings` | 项目 JSON、绑定 JSON | 文件是否符合 ST 要求 |
| 4. 根据量测生成校准 | `calibrate` | 色块 NPZ、ISP 响应 JSON | 新的校准 JSON 文件 |
| 5. 拟合机内色表 | `fit` | 指向参考和真实校准的项目 JSON | 候选目录、色表、拟合报告 |
| 6. 生成更新与还原清单 | `prepare-transition` | 候选、精确 AP／CP、绑定、布局 | 正向／还原清单目录 |

### 1. 检查 DCP / CUBE

执行 `python lut.py inspect "参考文件路径"`，阅读终端输出。这一步确认文件能否解析，并列出规格和 SHA-256；哈希可以理解为文件内容的指纹。DCP 会列出解析到的配置、色表／曲线信息；CUBE 会列出格点数和输入域。

**完成标准：**操作成功结束，没有文件格式错误。它不输出机内色表，也不证明色彩适合 Sony ST。特别是给 F-Log、S-Log 等视频素材使用的 LUT，输入起点不同，还需要经过量测的输入域映射。不要仅因扩展名为 `.cube` 就认为能直接导入。

### 2. 查看 ST 栏位计划

选择前面准备的 `project.json`。工具读取并显示计划，**这里没有编辑器，不会替你选择或修改栏位**；要改计划，回到文本编辑器修改 JSON，再执行一次。

只导入自定 1 时，日志应显示 `selected_slots` 为 `[1]`，`preserve_slots` 为 `[2, 3, 4, 5, 6]`，所选基础外观为 ST。校准和 DCP 还没齐全时，也可以先查看这个计划；计划成功不代表已经具备拟合或安装条件。

**完成标准：**目标栏位、名称和 ST 要求符合你的意图，没有误选要保留的栏位。

### 3. 核对 ST 绑定文件

“绑定”就是记录某个自定栏位当前使用哪个基础创意外观。此方案只在所导入栏位以 ST 为基础时使用新色表；基础改成其他外观会关闭导入效果，菜单本身没有被硬锁。

输入项目 JSON 和 `bindings.json`。若实际已核对自定 1 使用 ST，文件形式可以是：

```json
{"1": "ST"}
```

这只是格式示例。**此命令只检查文件中的声明，不会连接相机，也不会检查实际保存／运行值。** 不能为了让检查通过，凭空把所有栏位填成 ST；设备阶段仍需另行读取、核对实际状态。

**完成标准：**日志包含 `bindings_match: true`。它只表示两份文件在所选栏位上符合要求，不是实机已经通过检查。

### 4. 根据量测生成校准

这一步回答“工具计算中的 Sony ST 颜色，怎样对应到实际图像，以及原生色表的改动会怎样影响颜色”。它需要两种已经准备好的数据：

- **色块 NPZ：**装有成对颜色数值的文件，不是照片。每组数据包含 Sony ST 颜色和同一位置的线性 ProPhoto RGB／D50 RAW 显影颜色，还要区分训练与留出样本。
- **ISP 响应 JSON：**记录原生色表修改如何影响 RGB 的实测响应矩阵及量测来源。ISP 就是相机内部的图像处理流程。

取得这些数据，需要固定曝光／白平衡的匹配 RAW＋ST 样本、RAW 显影、图像对齐、色块提取，以及另行核验的 ISP 响应量测。**当前命令行工具不负责这些采集、处理和设备量测，也没有“选几张照片自动校准”的入口。** 如果你没有这些数据，需要由熟悉色彩与设备研究的人准备；只下载一个 DCP 还不足以完成本步骤。

向 `calibrate` 依次传入 `measurements/patches.npz`、`measurements/response.json` 和新输出文件 `calibration-v1.json`。已有有效的真实校准可以复用，无需重复生成。不能把照片改名成 NPZ，也不能用单位矩阵冒充量测结果。

**完成标准：**生成校准 JSON，并能说明样本与响应数据的来源。将项目 JSON 的 `calibration` 指向它。工具还会报告留出样本误差；单场景拟合较好不等于在所有场景准确。具体字段和数据要求见[数据格式](technical/formats.md)。

### 5. 拟合机内色表

选择已经指向真实参考文件和校准文件的项目 JSON，输出使用新的 `candidate-v1` 目录。工具尝试用 Sony 可存放的格点和系数，尽量逼近参考风格。

只选择栏位 1 时，完成后应看到：

```text
candidate-v1/
  candidate.json
  slot1.raw-s8.bin
```

`candidate.json` 是报告，包含来源／校准指纹、栏位计划和拟合误差；`.bin` 是色表数据。每款原生表为 5×9×9×3 有符号 7 位、1,215 字节。六款不会额外降低这一原生精度，但高分辨率 DCP 压到这张较小的表，仍不能完整保留每个原始条目。

**完成标准：**所选栏位都有色表，报告中的 `looks[].fit.convergence.converged` 为 `true`，且误差已经检查。`synthetic_holdout.rgb_mae` 越小，表示在该计算模型中越接近目标；它不是实拍色差分数，没有适用于所有风格的统一合格线。候选出现 `actual_photos_or_live_preview_verified: false` 是预期结果，因为尚未安装和拍照验证。

### 6. 生成更新与还原清单

现在需要候选目录、绑定 JSON，以及相机程序的两个完整文件：`appFw.so`（AP）和 `cpapp-b.bin`（CP）。它们需由另行核验的设备流程从目标机身取得，不在参考 DCP 包里，也不能用别人的备份代替。

指定 `--layout` 参数时：`full7-v4` 对应工具明确支持的六款版本；`three-preview-v2` 对应明确支持的历史三款版本。**不能只看相机显示 2.01 就随便选一个。原厂 2.01 并不等于这两种已修改来源。** 工具还会比较完整文件指纹；未经支持的来源会被拒绝。

输入正确的候选和文件后，输出使用新的 `transition-v1` 目录，生成：

```text
transition-v1/
  forward.private.json
  reverse.private.json
```

正向清单描述如何从这个精确原文件换成新表；还原清单描述如何从对应结果改回。二者都不是可放到 SD 卡里更新的 Sony 固件，也不是对任意损坏都有效的恢复包。保留候选、来源文件和清单，不公开机身原档及私人衍生清单。

**完成标准：**两份清单都生成，所选栏位、来源和前后指纹符合预期。名称、实际栏位设置、设备写入、重新加载和实拍验证尚未完成；此时不要把文件复制到相机里当作安装，也不要用 FL23 安装器代刷这些自定义数据。

## 从转换文件到真正装入相机：第 7–13 步

这一段是完整流程的设备部分。**当前公开工具的第 1–6 个转换命令可运行；第 7–13 步尚未封装为通用安装命令，需要 AI 按下列要求实现并验证。** 下面不会给你一个实际不存在的“点击安装”按钮，也不会让你把私人研究脚本复制到另一台机身直接执行。

给 AI 的任务可以直接写成：

> 阅读本页、AGENTS.md 和实现教程。我的目标是将指定 DCP／CUBE 安装到指定自定栏位，完成实际写入、读回、冷加载、预览和新照片验证，并提供还原。复用现有离线转换、USB 通讯和原生写入器源码；为我的机身创建新工作目录、两份核对备份及阶段日志。先识别来源，再选择“已有六款更新”或“首次安装”路径。实现并测试缺少的设备模块，逐阶段交付证据，不要在生成候选或清单时宣布安装完成。结果未知时先恢复证据，不重发写入。

### 7. 识别机身，选择首次安装或更新路径

Windows 用户按 [FL23 说明中的 USB 部分](fl23.md#3-连接相机并准备-usb-驱动)准备数据线、大量存储模式及驱动。AI 的自定义安装模块应复用 `src/fl23/transport.py` 的通讯能力，读取机型和机身身份摘要，再读取完整 AP／CP、当前设置、名称资源及保留启动镜像状态。**这里只复用通讯源码，不使用 FL23 的 install 命令代刷自定义数据。**

这里必须分两条路径：

| 机身起点 | 应做的事 | 现成代码到哪一步 |
|---|---|---|
| 已安装精确支持的 full7-v4 六款版本 | 更新选中栏位的色表；默认保留程序指令、名称、配方及未选栏位 | `six.replace_tables` 和 `worker.prepare_table_worker` 可离线准备受保护的原生编译输入；USB 执行编排仍待实现 |
| 原厂 2.01、仅装 FL23、其他自定义版本 | 先实现对应来源的首次安装适配器，再加入色表、运行路径、名称和栏位设置 | `sixbuild.build` 只支持历史三款来源，不能直接用于原厂或 FL23 来源；首次安装适配器仍需 AI 实现 |

**确认方式：**以完整文件 SHA-256 选择适配器，不以版本页面、文件名或“看起来是同一机型”放行。新的适配器必须记录明确的来源身份并通过离线复现和逆向测试；不能删除原有指纹检查来接收未知来源。具体哈希与源码入口见[AI 实机安装实施教程](lut-ai.md)。

### 8. 保存这台机身的两份备份和安装计划

AI 应在第一次设备修改之前保存：完整 AP／CP、实际将改动的名称资源、RAM 和保存两份设置视图、原自定配方、受保护 CP 单元，以及每个文件的长度和哈希。第二份副本放在独立位置，逐文件读回核对。不能把历史配方快照当作当前机身的新鲜备份。

安装计划应明确：机身身份、来源和目标指纹、目标栏位、每一项程序／资源／设置改动、所需电量、逆向产物和当前阶段。用户先核对“写到哪些栏位、保留哪些栏位、是否改名称”。正式写入前，实际电量至少 50%，并保持持续连接；本地原生只校验还必须成功。

**完成标准：**两份备份内容一致，目标文件和字段的当前值满足安装计划，所有阶段有对应还原方案。缺备份、缺逆向或源文件变化时，保持未写入状态。

### 9. 在电脑生成并测试真正的安装材料

已有六款、只换色表时，先完成第 6 步，再用公开的 `looktool.worker.prepare_table_worker` 校验正向／还原清单，生成针对本次来源和目标的 C 编译头与报告契约。AI 将它与 `src/fl23/native/installer.c` 编译成新的原生 worker；不能直接使用按 FL23 固定补丁编译的现成 `installer.so`。

首次安装还需构建来源适配器、名称资源转换及栏位设置计划。现有三款→六款构建器和完整六款复现测试是参考；要从原厂起步，AI 必须实现并检查对应程序差异、加载范围和所有入口。不能用已退役的 `bootstrap6` 绕过这些步骤。

**完成标准：**所有产物绑定本次来源；正向后再逆向能逐字节还原原档；原生检查、写入、故障和还原测试通过。具体编译和结果 ABI 见实施教程。编译或模拟通过仍不等于相机已安装。

### 10. 正式写入：资源、程序、设置分别执行

这是需要 AI 新实现设备执行器的步骤。用户不应手动往 `/usr` 或 `/cp` 复制固件文件。执行器应复用经核对的服务连接，将**本次编译且哈希固定的 worker**及模式请求暂存、读回核对，记录调用意图，然后执行一次。

- **已有六款的数据更新：**只执行已经审查的色表／校验值窗口。不为换表而重写名称或重置所有配方。
- **首次安装且需要新名称：**先以独立原子资源交易安装并核对匹配的名称资源，再安装引用它们的 AP／CP 程序，最后按新鲜字段计划保存选中栏位的 ST 及调整值。每段成功后才推进下一段。
- **栏位设置：**只写这次选中且已定位的字段，逐字段读回；保存后再核对保存视图。ST 基础要求不等于菜单被锁定，未选栏位和原有 FL／FL2／FL3 必须保留。

原生程序模式为 0=检查、1=安装、2=还原。主机必须校验完整的原生结果及本次来源／目标指纹。超时或断线可能发生在设备已执行后；此时先查已有结果，**不能因为电脑没收到完成消息就再次发送安装**。

**完成标准：**每项设备交易都有已验证的结果、完整日志和独立读回。仅“文件上传成功”或“进度条结束”不算安装成功。

### 11. 完整读回，并核对没有误改其他设置

AI 应通过主机独立读回**完整** AP／CP 文件，比较目标长度和 SHA-256；名称资源改过时也需逐文件完整读回。核对文件大小／inode、只读挂载恢复和已知临时文件清理。

对比写前与写后的 RAM／保存设置：所选字段应为计划目标，未选配方及受保护 CP 单元应保持。发现额外变动时，先用独立只读证据解释，不可整体忽略所有差异。

**完成标准：**原生完整哈希与主机完整读回均通过，设置保留检查通过，现场不存在结果未知的交易。程序在磁盘上更新与运行中加载了新版是两件事。

### 12. 重新加载，再验证预览和新照片

AI 先只读检查保留启动镜像：已知 mode2 状态只有满足对应前提时才执行一次受保护的失效处理；已经是 mode0 时核对现状，不重跑 mode2→0。状态不明时先停下来检查。

所有读写结束后，用户拔掉 USB 和其他供电，正常关机，等存取灯熄灭，取电池至少一分钟后开机。随后分别检查：名称显示、不按快门的预览切换、各选中外观的新照片和回放、原有 ST／FL／FL2／FL3。预览卡色而照片正确时，按预览路径排查，不重拟合已经正确的色表。

再连接后，AI 读取新的启动证据、AP 运行片段、完整 CP 磁盘文件及实际配方，保存本次加载核对报告。内核新启动和 CP 文件匹配不等于直接读到运行中的 CP 指令；未做的检查必须明确保留。

**完成标准：**写入、读回、加载证据以及用户观察均记录；未按快门的预览和新照片分别通过。不能只凭菜单名称出现就结束整个任务，也不能从单次成功承诺长期或所有机身稳定。

### 13. 需要撤销时，按本次交易还原

还原执行器也是 AI 需要实现、测试并交付的部分。对已完成的仅换表交易，先检查当前完整程序是否等于本次目标，再由同一个固定 worker 的 mode2 还原到本次来源，接着执行完整读回与重新加载验收。逆向清单是依据，不是一个可直接写入相机的更新包。

首次安装的还原按已验证的依赖逆序执行：恢复这次改动的选中设置、恢复引用关系兼容的程序、再恢复名称资源；不能在程序仍引用新名称时先删除资源。每一步检查当前值、只恢复本次目标，不回填整个旧设置快照覆盖用户后续改动。

若发生部分写入、结果未知或服务连接不可用，应先恢复已有交易证据、判断剩余能力，再制定恢复方案。不要把“没有成功回执”当作“没有写入”，也不要承诺任意损坏都可自动还原。

## 完整交付时，AI 必须留下什么

1. 实际存在、帮助信息和测试均匹配的设备命令／界面；不能只交付转换器。
2. 当前机身的新鲜双份备份，以及安装／逆向产物的哈希记录。
3. 名称、程序、设置三类交易的执行与完整读回证据；仅换表时明确哪些交易不需要。
4. 重新加载检查、用户预览／新照片测试结果及仍未验证的项目。
5. 可以检查未知结果并继续已知阶段的恢复方法，和已经测试的还原路径。

面向 AI 的源码位置、原生请求／结果 ABI、资源格式、设置定位规则和测试矩阵都在[实机安装实施教程](lut-ai.md)。它区分已实现函数和待开发接口，不会把研究机身的成功交易当成通用安装器已经存在。

## 常见卡点

| 现象 | 含义及下一步 |
|---|---|
| 项目文件报错 | 检查 JSON 逗号／引号、机型与固件字段、唯一栏位、`base: "ST"` 和来源署名 |
| 第 2 步通过，第 5 步找不到文件 | 查看计划不要求所有文件已存在；核对参考和校准路径是否相对于项目 JSON |
| 没有 NPZ／响应 JSON | 缺少量测前置条件；先准备数据，不能通过默认值补齐 |
| 输出已存在 | 保留原结果，选新文件名或新目录；工具避免覆盖旧产物 |
| 来源哈希不符或未收敛 | 需要检查来源版本或拟合结果；不要删除保护来强行生成 |
| 文件生成了，相机没变化 | 正常，所有六项操作都只在电脑执行 |
