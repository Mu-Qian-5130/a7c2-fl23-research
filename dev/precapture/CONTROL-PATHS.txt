# Native control-path comparison (offline)

This branch does **not** implement working camera pre-capture. This audit
identifies original code that can inform an implementation; it generates
private evidence and never connects to or modifies a camera.

Run with Capstone and private original firmware:

```text
python dev/precapture/audit_control.py --firmware-root PRIVATE_FIRMWARE_FOLDER --output NEW_PRIVATE_REPORT.json
```

The audit pins both CP image hashes, checks actual instructions and direct
branches, decodes the original priority branch tables, and checks task names,
ID arrays and configuration records. All code addresses below are **file
offsets**; firmware pointers have a separate `0x108000` load bias.

The target S1 controller calls its original start wrapper at `0x3ad540` and

## Queue-task ownership

The donor task-name clue now has a corresponding configuration and object
binding:

- Task ID 174 (`CAP_PRECAP_CTL`): descriptor file `0xe69c90`, entry pointer
  `0xbd879d`, stack size `0x2000`. Kernel task setup at `0x532480` onward
  indexes the descriptor array using `(task_id - 1) * 40`.
- Constructor `0xa9dce4` binds task ID `0xae` and message queue `0x51`
  to the task object at VA `0x192aecc`.
- Startup `0xa9dab2` passes that object to `0xad07d6` using a tail branch.
- The shared entry `0xad079c` retrieves the runtime callback object; its
  configured callback is the generic message loop at `0x4585e8`.
- Queue configuration/event producers at `0x3b8c00` / `0x3b8c60` enqueue
  callbacks to this task. Thus the task name alone does not identify a
  sensor-start routine.

The target already schedules its Timeshift queue through a different owner:

- `0xa0589e` starts the task object at VA `0x1a3aae0` and passes it to
  `0xa09a8e`, which stores it at VA `0x1a45ca4`.
- Constructor `0xa05d8e` configures task ID `0x88` and queue `0x38`.
  ID 136 maps to `CAM_CAP_MGR`, with descriptor file `0xdab60c`,
  shared entry pointer `0xb435a3`, and stack size `0x2000`.
- Original queue configuration/event producers `0xa09aee` / `0xa09b34`
  load this stored owner and call callback enqueue `0x407f1c`.

This resolves the original owner of the **existing target retention queue**.
It does not establish that new sensor work can run in that task context, or
resolve the missing asynchronous `0x4173` enable path. Preserve the native
callback lifetime, queue failure handling and OS protection.

## Remaining implementation boundary

Trace the capture-message receiver and its pre-S2 sensor/driver sequence,
identify actual pixel buffers and their lifetime, and connect settings,
enable, S1/S2, retention, recording and cancellation without disturbing
ordinary shooting. Native queue capacity is metadata capacity. Offline
matching and valid readbacks do not establish camera boot or shooting safety.

No flashable candidate has been produced from this audit.

constructs request0x20 with operation0x55, checks reply0x8020 and status,

Its caller is0x392e92. Release0xa04fe6 calls0xa13a60 ->0x408fdc

Donor allocation0xa98eb6 instead uses frame+0x5c60 and extra wrappers.
Those wrappers0xa948c0/0xa948d0 end in0xa94544/0xa94546, both BX LR.
They are no-ops, not evidence of extra reference counting. Do not transplant
the donor fields or release routine; the rest of lifetime handling differs.

Original target stage0xa0dd98 submits the instance to the retention
queue via0xa09b34. Its surrounding scheduler/lifetime calls still need
to be connected to RAW ownership and the later release path. No native
RAW service was executed and no RAW pixel contents were acquired in
these offline runs. Real capacity must come from the actual configured
pixel pool, not the metadata-node count.

## Code-generation correction

Zig0.13 with arm-linux-gnueabi plus -mthumb emitted ARM functions. Earlier
compiled comparisons established32-bit ARM semantics, not the claimed Thumb
ISA. The new thumb-linux-gnueabi target and explicit CPU feature exclusions
produce real Thumb function pointers and no FP/SIMD dependencies. Every
generated ELF is checked through its ISA mapping symbols, excluding literal
pools; wrong ISA, FP/SIMD and missing symbols are rejected. Old ARM and old
Thumb-with-NEON artifacts were confirmed rejected. Codec, retention, capture
gate, CP control, AP marshalling, S1 trigger and deferred-ring suites have
been rerun with these checks. No research ELF has been uploaded to a camera.

The full linked backend is larger than the geometric rodata tail. Neither
zero padding nor existing functions are approved storage. Executable
placement, real boot loading and all live task hooks remain unresolved.

## Native AP pending-record lifecycle

The real target capture_start_proc call at0x34a7b44 invokes deque push
helper0x34a144c for owner+0x320. On a preallocated, valid synthetic block,
this copies a24-byte pending group and advances end+0x30. The original

that can be bypassed with an assertion patch. PreS2 data must stay in the
correct CP retention path; normal data delivery requires its real AP task.
No fake AP job is injected, and this is not physical pre-capture acceptance.
